01 · Overview

Naive joins silently corrupt historical analytics.

This project proves it with a real, dated GICS sector reclassification — and fixes it with proper SCD Type 2 modeling.

On September 21, 2018, S&P Dow Jones Indices and MSCI created a new GICS sector, Communication Services, and reassigned companies like Alphabet, Meta, and Netflix out of Technology and Consumer Discretionary. On March 17, 2023, Visa, Mastercard, and PayPal moved from Technology to Financials. Any report or backtest that joins historical returns to a company's current sector — instead of the sector in effect on the trade date — is quietly rewriting history for every year that gap existed.

That's not an invented business rule. It's a real, externally-verifiable classification-committee decision with a public paper trail — which makes it a cleaner point-in-time correctness case study than most.

02 · Architecture

Bronze → Silver → Gold → Serving

No Airflow, on purpose — this project stays SQL-first. Orchestration runs through a scheduled GitHub Actions job (dbt build && dbt test).

Three source tables, landed as-is, no transformation.

sp500_membership — ticker list by date since 1996 (fja05680/sp500)
sp500_current_snapshot — current GICS Sector / Sub-Industry per ticker
daily_prices — OHLCV per ticker, 2015–2025 (Kaggle)

Where the point-in-time dimension actually gets built.

sector_history — curated seed table: ticker, old_sector, new_sector, effective_date, source_url
dim_sector_scd — hand-rolled SCD2 output: valid_from / valid_to / is_current
dim_sector_scd_dbt — same result, reproduced via dbt snapshot (check_cols)

Range join on trade date, plus the naive comparison for the anchor metric.

fact_returns_pit — daily return joined to the sector valid on the trade date
sector_return_comparison — naive vs. point-in-time correct, by sector and period

Public dashboard with the naive-vs-correct toggle and dbt test status — deployed on Streamlit Community Cloud, $0/month.

03 · SQL Depth

Four techniques, one mechanism

Window functions to detect the change, hand-rolled SCD2 to understand it, dbt to automate it, a recursive CTE to audit it, and a range join to actually use it correctly.

Daily returns per ticker via LAG, plus flagging the exact row where a ticker's sector label changes.

-- Compute daily returns and locate sector-change boundaries
WITH daily_returns AS (
    SELECT
        ticker, trade_date, close_price,
        LAG(close_price) OVER (
            PARTITION BY ticker ORDER BY trade_date
        ) AS prev_close,
        (close_price / LAG(close_price) OVER (
            PARTITION BY ticker ORDER BY trade_date
        ) - 1) AS daily_return
    FROM bronze.daily_prices
),
sector_versions AS (
    SELECT
        ticker, gics_sector, effective_date,
        LEAD(effective_date) OVER (
            PARTITION BY ticker ORDER BY effective_date
        ) AS next_change_date,
        ROW_NUMBER() OVER (
            PARTITION BY ticker ORDER BY effective_date
        ) AS version_number
    FROM silver.sector_history
)
SELECT * FROM daily_returns;

The mechanism itself — close the currently-open row, insert the new one. No ORM, no dbt macro hiding what's happening.

-- Close the currently-open row for any ticker with a new sector event
UPDATE dim_sector_scd d
SET valid_to = s.effective_date - INTERVAL '1 day',
    is_current = FALSE
FROM staging_sector_events s
WHERE d.ticker = s.ticker
  AND d.is_current = TRUE
  AND s.effective_date > d.valid_from;

-- Insert the new current row
INSERT INTO dim_sector_scd (
    ticker, gics_sector, gics_sub_industry,
    valid_from, valid_to, is_current
)
SELECT
    s.ticker, s.new_gics_sector, s.new_gics_sub_industry,
    s.effective_date, NULL, TRUE
FROM staging_sector_events s
WHERE NOT EXISTS (
    SELECT 1 FROM dim_sector_scd d
    WHERE d.ticker = s.ticker AND d.valid_from = s.effective_date
);

Walks a ticker's full sector version chain — the "linked list of changes" pattern interviewers ask for directly.

-- Walk GOOGL's full sector version chain
WITH RECURSIVE sector_chain AS (
    SELECT ticker, gics_sector, valid_from, valid_to, 1 AS depth
    FROM dim_sector_scd
    WHERE ticker = 'GOOGL'
      AND valid_from = (
          SELECT MIN(valid_from) FROM dim_sector_scd WHERE ticker = 'GOOGL'
      )

    UNION ALL

    SELECT d.ticker, d.gics_sector, d.valid_from, d.valid_to, c.depth + 1
    FROM dim_sector_scd d
    JOIN sector_chain c
      ON d.ticker = c.ticker
     AND d.valid_from = c.valid_to + INTERVAL '1 day'
)
SELECT * FROM sector_chain ORDER BY depth;

-- depth 1: Internet Software & Services   (Information Technology)   ... → 2018-09-20
-- depth 2: Interactive Media & Services   (Communication Services)   2018-09-21 → current

The technical core of the whole project: join every trade to the sector that was actually valid that day — and, for comparison, to today's sector too.

-- Gold layer: point-in-time correct join, alongside the naive one
SELECT
    f.ticker, f.trade_date, f.daily_return,
    d.gics_sector      AS sector_at_trade_date,
    d_naive.gics_sector AS sector_today
FROM silver.fact_returns f
JOIN dim_sector_scd d
  ON f.ticker = d.ticker
 AND f.trade_date BETWEEN d.valid_from
                       AND COALESCE(d.valid_to, DATE '9999-12-31')
JOIN dim_sector_scd d_naive
  ON f.ticker = d_naive.ticker
 AND d_naive.is_current = TRUE;

06 · Data Quality

dbt tests — temporal integrity

Because a point-in-time dimension is only as trustworthy as its guarantees against overlap and gaps.

-- tests/no_overlapping_validity_ranges.sql
SELECT a.ticker, a.valid_from, a.valid_to, b.valid_from AS overlapping_from
FROM dim_sector_scd a
JOIN dim_sector_scd b
  ON a.ticker = b.ticker AND a.valid_from < b.valid_from
WHERE a.valid_to IS NULL OR a.valid_to >= b.valid_from;
-- test fails if this returns any rows
-- tests/exactly_one_current_row.sql
SELECT ticker, COUNT(*) AS current_rows
FROM dim_sector_scd
WHERE is_current = TRUE
GROUP BY ticker
HAVING COUNT(*) != 1;
-- tests/fact_dimension_referential_integrity.sql
SELECT f.ticker, f.trade_date, COUNT(d.ticker) AS matches
FROM fact_returns_pit f
LEFT JOIN dim_sector_scd d
  ON f.ticker = d.ticker
 AND f.trade_date BETWEEN d.valid_from AND COALESCE(d.valid_to, DATE '9999-12-31')
GROUP BY f.ticker, f.trade_date
HAVING COUNT(d.ticker) != 1;
-- tests/reclassified_ticker_has_multiple_versions.sql
-- directly checkable against sector_history because every event
-- is a documented source, not a derived assumption
SELECT s.ticker, COUNT(d.ticker) AS dimension_rows
FROM silver.sector_history s
JOIN dim_sector_scd d ON s.ticker = d.ticker
GROUP BY s.ticker
HAVING COUNT(d.ticker) < 2;
07 · Business Impact

The anchor metric

The number that turns "I can write advanced SQL" into something a recruiter understands in five seconds.

Recalculating cumulative sector returns for Information Technology and Communication Services, [YYYY–YYYY], using each stock's GICS sector as classified on the trade date instead of today's classification, changed the reported return of [sector] by [X pp] and reassigned [Y] companies' historical performance out of a sector that, for [Z%] of the period measured, did not yet exist.

X / Y / Z populate after Phase 4 executes against the real warehouse — held as placeholders, not estimated, per this project's technical-honesty standard.
Financial / audit

Misstatement risk in sector-return figures feeding factsheets, ETF marketing material, and performance-attribution reports.

Regulatory

SEC / FINRA disclosure integrity for sector-based investment products — a live compliance concern, not an analogy.

ML / leakage

Training a sector-classification or sector-momentum model on backfilled labels is target leakage — the same mechanism as AdEngine's temporal anti-leakage validation.
